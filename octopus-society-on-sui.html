Building an Octopus Society on Sui

This sample uses an interview format to explain why Sui is a strong architectural fit for a multiplayer blockchain game where each player embodies a single octopus living in a shared ocean society, trading unique objects and maintaining communal farms.

Interview format

Why Sui fits the concept

The sections below show how the platform choice is justified through gameplay requirements such as identity, ownership, shared state, scalability, and trust.

Setting the scene

Concept framing · Multiplayer society design

Interviewer: Let's set the scene. This isn't a "collect and hoard" game — it's a society. Every player is one octopus, living among other octopi, trading shells and pebbles, farming mussels together. Why does that framing matter when you're choosing a blockchain?

Developer: Because it changes what actually needs to be true on-chain. A collection game just needs "player owns object." A society needs objects to move between many owners constantly, some objects to be jointly managed, and the whole thing to feel alive and responsive rather than like a spreadsheet with a shell icon.

That is a much higher bar for the underlying platform, and it is exactly the bar I used when I looked at Sui.

One player, one octopus

Persistent identity · On-chain player model

Interviewer: Start with the octopus itself. One player, one octopus — that's the player's identity in this world. What does that need from the chain?

Developer: It needs to be a genuine, persistent object, not a login record. On Sui, my octopus is a Move object with its own on-chain identity. Its age, territory, and relationships with other octopi can all live as fields on that one object.

The player does not just have an account that references an octopus somewhere in a database. The player holds the octopus itself. That distinction matters because it turns identity into something portable and durable inside the game world rather than something the studio can silently rewrite behind the curtain.

Shells, pebbles, and real ownership

Unique assets · Object ownership

Interviewer: So the octopus itself is an object. What about the shells and pebbles it collects and trades?

Developer: That is where Sui starts to feel especially natural. Shells and pebbles are not abstract balances. They are individual things with their own history, rarity, appearance, and significance. Sui's object model maps directly onto that idea, because every shell or pebble can be its own on-chain object rather than an entry in some global token ledger.

That means ownership is not simulated. If my octopus finds a rare shell, that shell can exist as a distinct asset my wallet controls. If I trade it to another octopus, I am transferring that specific object, not updating a number in a central database.

Trading without friction

Transfers · Marketplace logic

Interviewer: Trading sounds core to the social side of the game. Why is Sui a good fit there?

Developer: Because object transfer is a first-class concept. If octopi are constantly swapping shells, pebbles, crafted items, or rare finds, I need those exchanges to be reliable and cheap enough that players do not feel punished for participating in the economy.

Sui is designed around moving and mutating objects directly, which makes peer-to-peer exchange feel like part of the world instead of an awkward blockchain tax sitting on top of it. That matters in a social game, because if trading feels heavy, players stop doing it and the society starts to die.

Communal mussel farms

Shared objects · Group-owned game structures

Interviewer: Let's talk about the mussel farms. You said these have a community dimension — they're not purely solo. What does that require, technically?

Developer: It requires shared control over a single object, which is a genuinely hard problem on a lot of chains. A mussel farm is not owned by one octopus in the way a pebble is. It might be tended by several octopi who each contribute effort and each have a claim on what it produces.

On Sui, I can model a farm as a shared object — one that is not locked to a single owner's authority but can be referenced and mutated by transactions from multiple players, with the game's Move logic defining exactly who is allowed to do what. That is the difference between one player's private idle timer and a real communal structure that a group of octopi maintain together.

Day-to-day farm actions

Programmable Transaction Blocks · Multi-step player actions

Interviewer: How does that shared-object model affect the day-to-day feel of the game — an octopus checking on the farm, harvesting mussels, restocking it?

Developer: This is where Programmable Transaction Blocks earn their keep again, just at a bigger scale than a single-player action. A visit to the farm might involve checking the shared farm object, harvesting whatever is ready, updating that octopus's contribution record, and depositing mussels into that player's own inventory — all as one transaction the player approves once.

Because Sui's object model tracks exactly which objects a transaction touches — the shared farm, the player's own octopus, the mussels being minted — the network can process these efficiently even with lots of octopi visiting the same farm, without everything queuing up behind a single global bottleneck.

Parallel activity

Scalability · Non-conflicting transactions

Interviewer: Speaking of many players touching the same objects — doesn't a shared farm become a congestion point if fifty octopi want to harvest at once?

Developer: That is a real concern on chains where all state changes funnel through one global sequence. Sui's object-centric execution model is specifically built to parallelise transactions that do not actually conflict.

If two octopi are harvesting from two different farms, there is no reason those transactions should compete with each other, and Sui's architecture is designed to recognise that automatically. That is not just a nice side effect for me. It is close to a hard requirement once you accept that the whole premise of the game is many players interacting with shared community structures at once.

Randomness and trust

Fair outcomes · Verifiable game logic

Interviewer: Randomness comes up naturally too, I'd guess — what a pebble looks like when it's found, how much a farm yields this season.

Developer: Exactly, and the same argument applies here as it would in any game asking players to trust an outcome. If I want players to believe that finding a rare pebble or getting a strong harvest is genuinely down to chance and not something I quietly control server-side, that randomness needs to be verifiable, not just asserted.

Sui's built-in on-chain randomness lets me generate those outcomes in a way players can actually check, which matters even more in a society-style game because trust between the game and its community is the whole point.

Architecture in one paragraph

Backend · Wallet · Chain responsibilities

Interviewer: If you had to compress the architecture into one paragraph for a non-specialist stakeholder, how would you explain it?

Developer: The backend still matters — it can prepare actions, enforce game rules, and coordinate the player experience — but the actual identity objects, tradeable belongings, and communal structures live on-chain as Sui objects. The wallet approves important actions, the chain records who owns what and how shared structures change, and the result is a game world where social trust comes from the architecture itself rather than from a promise that the developer will behave.

Why this matters

Product reasoning · Platform fit

Interviewer: So the short version is that Sui is not just fast enough — it matches the structure of the game.

Developer: Exactly. If the game were just menus and cosmetics, I would not need all of this. But if the fantasy is a living society of octopi with real identity, distinct belongings, communal farms, constant trade, and meaningful chance, then Sui fits not as a marketing layer but as part of the actual design logic.

That is why I keep returning to it for this concept: the chain's object model, shared-object support, scaling approach, and verifiable randomness all line up with the world I want the player to believe in.
