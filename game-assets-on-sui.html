Start with a society, not a loot table

Narrative context · Web2 and on-chain design

Imagine you are building a game where each player is one octopus living among other octopi, trading shells and pebbles, tending communal mussel farms, and building a reputation in a shared tide pool.

In a traditional Web2 stack, that world is often represented as rows in a studio-controlled database. The octopus identity, the shells it owns, and the farm it helps maintain may all be stored as records the developer controls directly.

On Sui, those parts of the world can be modeled as on-chain objects defined in Move. The player can hold an octopus object in a wallet, own unique shells and pebbles directly, and interact with shared structures through explicit transaction logic.

The examples stay intentionally simplified and focus on object shape, transaction flow, and system boundaries rather than full production concerns such as sponsored transactions, indexing pipelines, retries, observability, or custody design.

Architecture at a glance

Game client · Backend service · Wallet · Sui network

One common Sui integration pattern still follows a familiar structure: the backend validates request context and prepares transaction data, while signing happens in a wallet or another explicitly trusted signer.

  • The game client calls your API, for example POST /api/octopus/v1/shells or POST /api/octopus/v1/farms/{farmId}/harvest.
  • Your backend validates the request, resolves current on-chain object inputs, and builds a transaction payload.
  • The payload is returned to the client for wallet approval, or routed to an authorized signer when the product flow requires service-controlled minting.
  • The signed transaction is submitted to the Sui network.
  • Your backend stores transaction digests, reads effects, and reconciles local metadata with the resulting on-chain object state.

This can keep the API familiar for application developers while making it clear that ownership, transfer, and mutation ultimately follow the Sui object model.

Before you start

Requirements · wallet · endpoint · package · indexing

  • A Sui wallet on testnet with SUI for gas, unless your flow uses sponsored transactions.
  • A current Sui full node or provider endpoint.
  • A published Move package for your octopus, shell, pebble, and farm types.
  • A backend service that can build transaction payloads and track transaction results.

Replace packageId, octopusObjectId, shellObjectId, farmObjectId, and wallet addresses with values from your environment. Keep private keys, admin capabilities, and RPC secrets out of client code and out of source control.

Move: define the core game objects

Smart contract logic · Identity object · Unique belongings

In this game, the first important object is not a weapon. It is the octopus itself. That object represents the player’s identity in the society, while shells and pebbles are unique belongings the octopus can own, trade, and carry between interactions.

On Sui, owned objects need a UID field and the key ability. If you want an object to be transferable with transfer::public_transfer, it also needs the store ability. 

module octopus_society::assets {
  use std::string::String;
  use sui::object::{Self, UID};
  use sui::transfer;
  use sui::tx_context::TxContext;

  public struct Octopus has key, store {
      id: UID,
      name: String,
      age: u64,
      territory: String,
      reputation: u64,
  }

  public struct Shell has key, store {
      id: UID,
      label: String,
      origin_reef: String,
      rarity: u8,
  }

  public struct Pebble has key, store {
      id: UID,
      shape: String,
      colour: String,
      rarity: u8,
  }

  public fun new_octopus(name: String, age: u64, territory: String, ctx: &mut TxContext): Octopus {
      Octopus {
          id: object::new(ctx),
          name,
          age,
          territory,
          reputation: 0,
      }
  }

  public fun new_shell(label: String, origin_reef: String, rarity: u8, ctx: &mut TxContext): Shell {
      Shell {
          id: object::new(ctx),
          label,
          origin_reef,
          rarity,
      }
  }

  public entry fun mint_octopus(name: String, age: u64, territory: String, recipient: address, ctx: &mut TxContext) {
      let octopus = new_octopus(name, age, territory, ctx);
      transfer::public_transfer(octopus, recipient)
  }

  public entry fun mint_shell(label: String, origin_reef: String, rarity: u8, recipient: address, ctx: &mut TxContext) {
      let shell = new_shell(label, origin_reef, rarity, ctx);
      transfer::public_transfer(shell, recipient)
  }

  public entry fun polish_shell(shell: &mut Shell, new_rarity: u8) {
      shell.rarity = new_rarity
  }

  public entry fun transfer_shell(shell: Shell, recipient: address) {
      transfer::public_transfer(shell, recipient)
  }

  public entry fun retire_shell(shell: Shell) {
      let Shell { id, label: _, origin_reef: _, rarity: _, .. } = shell;
      object::delete(id)
  }
}

This model follows the social structure used throughout this sample: one player, one octopus identity object, plus unique belongings that can circulate between players without being modeled as fungible assets.

1. Mint an octopus identity

POST /api/octopus/v1/identities · Create the player character

In this sample, onboarding begins by minting the player’s octopus identity rather than creating a generic account and attaching cosmetics later. The identity object anchors age, territory, and future social actions. 

curl -X POST "{base_url}/api/octopus/v1/identities" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer {player_session_token}" \
  -d '{
    "name": "Nerida",
    "age": 4,
    "territory": "Glass Kelp Ridge",
    "recipient": "{player_sui_address}"
  }'
import { Transaction } from '@mysten/sui/transactions';

const tx = new Transaction();
tx.moveCall({
  target: `${packageId}::assets::mint_octopus`,
  arguments: [
    tx.pure.string('Nerida'),
    tx.pure.u64(4),
    tx.pure.string('Glass Kelp Ridge'),
    tx.pure.address(playerAddress),
  ],
});

// Build the transaction for wallet approval or pass it to an authorized signer.

The flow produces an octopus identity object whose ID can be reused in later interactions and transaction flows.

2. Mint a unique shell

POST /api/octopus/v1/shells · Create an owned collectible

A shell is a unique, tradeable belonging with its own origin and rarity. That makes it a strong fit for a Sui object model rather than a value hidden behind a database row. 

curl -X POST "{base_url}/api/octopus/v1/shells" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer {player_session_token}" \
  -d '{
    "label": "Spiral Moon Shell",
    "origin_reef": "North Tide Hollow",
    "rarity": 3,
    "recipient": "{player_sui_address}"
  }'
import { Transaction } from '@mysten/sui/transactions';

const tx = new Transaction();
tx.moveCall({
  target: `${packageId}::assets::mint_shell`,
  arguments: [
    tx.pure.string('Spiral Moon Shell'),
    tx.pure.string('North Tide Hollow'),
    tx.pure.u8(3),
    tx.pure.address(playerAddress),
  ],
});

The flow produces a shell object owned by the player, with explicit origin and rarity that can later support trade and polish flows.

3. Polish a shell in place

PATCH /api/octopus/v1/shells/{objectId} · Mutate an owned object

Some changes should mutate the existing object instead of replacing it. Polishing a shell improves its rarity in place, and because the Move function takes &mut Shell, the transaction must include the current shell as a mutable input. 

curl -X PATCH "{base_url}/api/octopus/v1/shells/{objectId}" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer {player_session_token}" \
  -d '{
    "rarity": 5
  }'
import { Transaction } from '@mysten/sui/transactions';

const tx = new Transaction();
tx.moveCall({
  target: `${packageId}::assets::polish_shell`,
  arguments: [tx.object(shellObjectId), tx.pure.u8(5)],
});

The shell’s rarity increases while its identity and ownership remain unchanged, reinforcing the idea of object mutation instead of replacement.

4. Trade in the tide pool

POST /api/octopus/v1/trades · Direct transfer with room for marketplace expansion

In this sample, trading is modeled as a social exchange between octopi rather than as a generic store interaction. One octopus can transfer a shell directly to a neighbour, and a fuller marketplace implementation could extend that flow with Kiosk-style listing, discovery, settlement, and transfer. 

curl -X POST "{base_url}/api/octopus/v1/trades" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer {seller_session_token}" \
  -d '{
    "object_id": "{shell_object_id}",
    "buyer_address": "{buyer_sui_address}",
    "price_token": "SUI",
    "price_amount": 10,
    "trade_note": "Three bright pebbles and one rare shell would also work in a custom flow."
  }'
import { Transaction } from '@mysten/sui/transactions';

const tx = new Transaction();
tx.moveCall({
  target: `${packageId}::assets::transfer_shell`,
  arguments: [tx.object(shellObjectId), tx.pure.address(buyerAddress)],
});

// In a fuller marketplace flow, your backend could instead prepare Kiosk listing or purchase calls and return them for wallet approval.

The shell moves from one player to another through a direct transfer in this example, while a marketplace pattern can build on the same object model and transaction flow.

5. Model a communal mussel farm

Shared object · Multi-player structure

A mussel farm is a communal structure that several octopi can interact with. That makes it a stronger fit for a shared object than for an individually owned object. 

module octopus_society::farm {
  use sui::object::{Self, UID};
  use sui::tx_context::TxContext;

  public struct MusselFarm has key {
      id: UID,
      total_mussels_ready: u64,
      last_harvest_epoch: u64,
  }

  public fun new_farm(total_mussels_ready: u64, last_harvest_epoch: u64, ctx: &mut TxContext): MusselFarm {
      MusselFarm {
          id: object::new(ctx),
          total_mussels_ready,
          last_harvest_epoch,
      }
  }

  public entry fun restock_farm(farm: &mut MusselFarm, added_mussels: u64) {
      farm.total_mussels_ready = farm.total_mussels_ready + added_mussels;
  }

  public entry fun harvest_farm(farm: &mut MusselFarm, harvested: u64, current_epoch: u64) {
      farm.total_mussels_ready = farm.total_mussels_ready - harvested;
      farm.last_harvest_epoch = current_epoch;
  }
}

The same farm object can be referenced and mutated by multiple players through game rules, which makes it a useful example of shared state on Sui.

6. Harvest with a Programmable Transaction Block

POST /api/octopus/v1/farms/{farmId}/harvest · Introduce bundled transaction logic

A trip to the farm is rarely a single isolated state change. In one visit, an octopus may check the shared farm, harvest what is ready, update its own contribution trail, and receive mussels into personal inventory.

Programmable Transaction Blocks help here by letting the player approve a bundled flow instead of a chain of disconnected mutations. 

curl -X POST "{base_url}/api/octopus/v1/farms/{farm_object_id}/harvest" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer {player_session_token}" \
  -d '{
    "octopus_id": "{octopus_object_id}",
    "harvest_amount": 8,
    "deposit_to_inventory": true
  }'
import { Transaction } from '@mysten/sui/transactions';

const tx = new Transaction();
tx.moveCall({
  target: `${packageId}::farm::harvest_farm`,
  arguments: [tx.object(farmObjectId), tx.pure.u64(8), tx.pure.u64(currentEpoch)],
});

// In a fuller PTB, you could also:
// - update the player's octopus contribution record
// - mint or transfer harvested mussels into player inventory
// - attach additional bookkeeping calls before submission

This example shows the starting point for a PTB-based harvest flow by updating the communal farm within a transaction that can later be expanded with player-specific actions.

7. Fair randomness for discovered items

Rarity outcomes · Trust in shared systems

Randomness matters in this game too. A newly discovered pebble may vary in shape, colour, or rarity, and a seasonal farm event may produce an unexpectedly strong yield.

The goal is not only surprise but trust. If the game says that a rare shell or pebble came from chance, players should be able to treat that outcome as a chain-backed result rather than a server-side claim they simply have to accept.

Retire a shell when it leaves the world

DELETE /api/octopus/v1/shells/{objectId} · Remove the object

Some objects should disappear permanently. When a shell is intentionally retired from the world state, the game should consume the object and delete its UID so it is no longer available for transfer or mutation. 

curl -X DELETE "{base_url}/api/octopus/v1/shells/{objectId}" \
  -H "Authorization: Bearer {player_session_token}"
public entry fun retire_shell(shell: Shell) {
    let Shell { id, label: _, origin_reef: _, rarity: _, .. } = shell;
    object::delete(id)
}

Retiring the shell removes it from circulation and makes any future attempt to reference it an error, which keeps the world state consistent with the narrative.

Error handling and finality

Gas, stale references, execution status, reconciliation

Blockchain flows introduce failure modes that a REST-only system does not: insufficient gas, signature rejection, stale object references, and on-chain execution errors.

  • Model transaction creation, signature approval, submission, execution, and indexed state as separate states.
  • Rebuild transactions when object references become stale.
  • Store transaction digests and reconcile backend metadata from transaction effects.
  • Avoid treating API acceptance as final success until on-chain execution is confirmed.
  • Be especially careful with shared objects such as communal farms, where concurrency and current object state matter directly to transaction validity.
