Manage on‑chain game assets with the Sui stack

A technical + storytelling tutorial showing how a game backend and client work with Move modules, wallet signing, and Sui objects to mint, upgrade, transfer, and retire player‑owned assets.

Back to portfolio

Story: Giving players real ownership

Narrative context · Web2 vs Web3

Imagine you are building an action RPG where players collect weapons, skins, and artifacts. In a traditional Web2 stack, each item is stored in a game database and controlled entirely by the studio.

On Sui, each item can be represented as an on‑chain object defined in Move. A player can hold that object in a wallet, transfer it, and prove ownership to other services directly on‑chain.

This tutorial shows how a game backend can expose a familiar API layer while the blockchain‑facing logic uses Sui objects and Programmable Transaction Blocks under the hood.

The examples are intentionally simplified. They focus on transaction shape, object flow, and responsibility boundaries rather than production concerns such as sponsored transactions, key custody, retries, monitoring, or indexing.

Architecture at a glance

Game client · Backend service · Wallet · Sui network

A common Sui integration pattern is to let the backend validate intent and prepare transaction data, while signing happens in a wallet or another explicitly trusted signer.

    >The game client calls your API, for example de>POST /api/game/v1/assets. >Your backend validates the request, resolves current on‑chain inputs, and builds a transaction payload. >The payload is returned to the client for wallet approval, or routed to an authorized signer when the business flow requires service‑controlled minting. >The signed transaction is submitted to the Sui network. >Your backend stores transaction digests, reads effects, and reconciles local metadata with on‑chain state.

This keeps your API developer‑friendly without hiding the fact that the source of truth for ownership and mutation is the Sui object model.

Before you start

Requirements: wallet, endpoint, package, indexing

    >A Sui wallet on testnet with SUI for gas, unless you use sponsored transactions. >A current Sui full node or provider endpoint. >A published Move package for your game asset types. >A backend service that can build transaction payloads and track transaction results.

Replace de>{package_id}, de>{asset_object_id}, and wallet addresses with real values from your environment. Keep private keys, admin capabilities, and RPC secrets out of client code and out of source control.

Move: Define the weapon asset

Smart contract logic · Sui object semantics

In Sui, owned objects need a de>UID field and the de>key ability. If you want an object to be transferable with de>transfer::public_transfer, it also needs the de>store ability. 

de>module game_assets::weapon {
  use std::string::String;
  use sui::object::{Self, UID};
  use sui::transfer;
  use sui::tx_context::TxContext;

  public struct Weapon has key, store {
    id: UID,
    name: String,
    power_level: u64,
    rarity: u8,
  }

  public fun new(
    name: String,
    power_level: u64,
    rarity: u8,
    ctx: &mut TxContext,
  ): Weapon {
    Weapon {
      id: object::new(ctx),
      name,
      power_level,
      rarity,
    }
  }

  public entry fun mint_weapon(
    name: String,
    power_level: u64,
    rarity: u8,
    recipient: address,
    ctx: &mut TxContext,
  ) {
    let weapon = new(name, power_level, rarity, ctx);
    transfer::public_transfer(weapon, recipient);
  }

  public entry fun upgrade_weapon(
    weapon: &mut Weapon,
    new_power_level: u64,
    new_rarity: u8,
  ) {
    weapon.power_level = new_power_level;
    weapon.rarity = new_rarity;
  }

  public entry fun transfer_weapon(
    weapon: Weapon,
    recipient: address,
  ) {
    transfer::public_transfer(weapon, recipient);
  }

  public entry fun burn_weapon(weapon: Weapon) {
    let Weapon {
      id,
      name: _,
      power_level: _,
      rarity: _,
    } = weapon;
    object::delete(id);
  }
}

This sample models a straightforward owned object lifecycle: mint, mutate, transfer, and delete. It is intentionally simple, but it matches Sui’s object‑based design much better than a pseudo‑database or legacy RPC‑style example.

1. Mint a weapon

POST /api/game/v1/assets · Create an owned object

When a player completes a quest or onboarding flow, your backend can build a transaction that calls de>mint_weapon. Depending on your product model, that transaction may be signed by the player, by a game‑controlled signer, or through a sponsored flow. 

de>curl -X POST "{base_url}/api/game/v1/assets" \
  -H "Authorization: Bearer {player_session_token}" \
  -H "Content-Type: application/json" \
  -d '{
    "type": "weapon",
    "name": "Blade of Dawn",
    "power_level": 12,
    "rarity": 3,
    "recipient": "{player_sui_address}"
  }'
de>import { Transaction } from '@mysten/sui/transactions';

const tx = new Transaction();

tx.moveCall({
  target: '{package_id}::weapon::mint_weapon',
  arguments: [
    tx.pure.string('Blade of Dawn'),
    tx.pure.u64(12),
    tx.pure.u8(3),
