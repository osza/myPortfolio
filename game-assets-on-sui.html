Start with a society, not a loot table

Narrative context · Web2 vs Web3

Imagine you are building a game where each player is one octopus living among other octopi, trading shells and pebbles, tending communal mussel farms, and building a reputation in a shared tide pool.

In a traditional Web2 stack, that world usually collapses into rows in a studio-controlled database. The octopus identity, the shells it owns, and the farm it helps maintain are all ultimately just records the developer can rewrite at will.

On Sui, those parts of the world can be modeled as on-chain objects defined in Move. The player can hold an octopus object in a wallet, own unique shells and pebbles directly, and interact with shared structures through explicit transaction logic.

This tutorial keeps the examples intentionally simplified. The focus is on object shape, transaction flow, and system boundaries rather than full production concerns such as sponsored transactions, indexing pipelines, retries, observability, or custody design.

Architecture at a glance

Game client · Backend service · Wallet · Sui network

A common Sui integration pattern is still the same: the backend validates intent and prepares transaction data, while signing happens in a wallet or another explicitly trusted signer.

  • The game client calls your API, for example POST /api/octopus/v1/shells or POST /api/octopus/v1/farms/{farm_id}/harvest.
  • Your backend validates the request, resolves current on-chain object inputs, and builds a transaction payload.
  • The payload is returned to the client for wallet approval, or routed to an authorized signer when the product flow requires service-controlled minting.
  • The signed transaction is submitted to the Sui network.
  • Your backend stores transaction digests, reads effects, and reconciles local metadata with the resulting on-chain object state.

This keeps the API familiar for application developers without hiding the fact that the source of truth for ownership, transfer, and mutation is the Sui object model.

Before you start

Requirements: wallet, endpoint, package, indexing

  • A Sui wallet on testnet with SUI for gas, unless your flow uses sponsored transactions.
  • A current Sui full node or provider endpoint.
  • A published Move package for your octopus, shell, pebble, and farm types.
  • A backend service that can build transaction payloads and track transaction results.

Replace {package_id}, {octopus_object_id}, {shell_object_id}, {farm_object_id}, and wallet addresses with real values from your environment. Keep private keys, admin capabilities, and RPC secrets out of client code and out of source control.

Move: Define the core game objects

Smart contract logic · Identity object · Unique belongings

In this game, the first important object is not a weapon. It is the octopus itself. That object represents the player's identity in the society, while shells and pebbles are unique belongings the octopus can own, trade, and carry between interactions.

On Sui, owned objects need a UID field and the key ability. If you want an object to be transferable with transfer::public_transfer, it also needs the store ability. 

module octopus_society::assets {
  use std::string::String;
  use sui::object::{Self, UID};
  use sui::transfer;
  use sui::tx_context::TxContext;

  public struct Octopus has key, store {
    id: UID,
    name: String,
    age: u64,
    territory: String,
    reputation: u64,
  }

  public struct Shell has key, store {
    id: UID,
    label: String,
    origin_reef: String,
    rarity: u8,
  }

  public struct Pebble has key, store {
    id: UID,
    shape: String,
    colour: String,
    rarity: u8,
  }

  public fun new_octopus(
    name: String,
    age: u64,
    territory: String,
    ctx: &mut TxContext,
  ): Octopus {
    Octopus {
      id: object::new(ctx),
      name,
      age,
      territory,
      reputation: 0,
    }
  }

  public fun new_shell(
    label: String,
    origin_reef: String,
    rarity: u8,
    ctx: &mut TxContext,
  ): Shell {
    Shell {
      id: object::new(ctx),
      label,
      origin_reef,
      rarity,
    }
  }

  public entry fun mint_octopus(
    name: String,
    age: u64,
    territory: String,
    recipient: address,
    ctx: &mut TxContext,
  ) {
    let octopus = new_octopus(name, age, territory, ctx);
    transfer::public_transfer(octopus, recipient);
  }

  public entry fun mint_shell(
    label: String,
    origin_reef: String,
    rarity: u8,
    recipient: address,
    ctx: &mut TxContext,
  ) {
    let shell = new_shell(label, origin_reef, rarity, ctx);
    transfer::public_transfer(shell, recipient);
  }

  public entry fun polish_shell(
    shell: &mut Shell,
    new_rarity: u8,
  ) {
    shell.rarity = new_rarity;
  }

  public entry fun transfer_shell(
    shell: Shell,
    recipient: address,
  ) {
    transfer::public_transfer(shell, recipient);
  }

  public entry fun retire_shell(shell: Shell) {
    let Shell {
      id,
      label: _,
      origin_reef: _,
      rarity: _,
    } = shell;
    object::delete(id);
  }
}

This gives you a cleaner fit for the society described elsewhere in the portfolio: one player, one octopus identity object, plus unique belongings that can circulate between players without pretending they are fungible tokens.

1. Mint an octopus identity

POST /api/octopus/v1/identities · Create the player character

In this world, onboarding is not "create a generic account and attach cosmetics later." It is "mint the player's octopus identity." That object becomes the anchor for age, territory, and future social actions. 

curl -X POST "{base_url}/api/octopus/v1/identities" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer {player_session_token}" \
  -d '{
    "name": "Nerida",
    "age": 4,
    "territory": "Glass Kelp Ridge",
    "recipient": "{player_sui_address}"
  }'
