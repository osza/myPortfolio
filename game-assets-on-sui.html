Giving players real ownership

Narrative context · Web2 vs Web3

Imagine you are building an action RPG where players collect weapons, skins, and artifacts. In a traditional Web2 stack, each item is stored in a game database and controlled entirely by the studio.

On Sui, each item can be represented as an on-chain object defined in Move. A player can hold that object in a wallet, transfer it, and prove ownership to other services directly on-chain.

This tutorial shows how a game backend can expose a familiar API layer while the blockchain-facing logic uses Sui objects and Programmable Transaction Blocks under the hood.

The examples are intentionally simplified. They focus on transaction shape, object flow, and responsibility boundaries rather than production concerns such as sponsored transactions, key custody, retries, monitoring, or indexing.

Architecture at a glance

Game client · Backend service · Wallet · Sui network

A common Sui integration pattern is to let the backend validate intent and prepare transaction data, while signing happens in a wallet or another explicitly trusted signer.

  • The game client calls your API, for example POST /api/game/v1/assets.
  • Your backend validates the request, resolves current on-chain inputs, and builds a transaction payload.
  • The payload is returned to the client for wallet approval, or routed to an authorized signer when the business flow requires service-controlled minting.
  • The signed transaction is submitted to the Sui network.
  • Your backend stores transaction digests, reads effects, and reconciles local metadata with on-chain state.

This keeps your API developer-friendly without hiding the fact that the source of truth for ownership and mutation is the Sui object model.

Before you start

Requirements: wallet, endpoint, package, indexing

  • A Sui wallet on testnet with SUI for gas, unless you use sponsored transactions.
  • A current Sui full node or provider endpoint.
  • A published Move package for your game asset types.
  • A backend service that can build transaction payloads and track transaction results.

Replace {package_id}, {asset_object_id}, and wallet addresses with real values from your environment. Keep private keys, admin capabilities, and RPC secrets out of client code and out of source control.

Move: Define the weapon asset

Smart contract logic · Sui object semantics

In Sui, owned objects need a UID field and the key ability. If you want an object to be transferable with transfer::public_transfer, it also needs the store ability. 

module game_assets::weapon {
  use std::string::String;
  use sui::object::{Self, UID};
  use sui::transfer;
  use sui::tx_context::TxContext;

  public struct Weapon has key, store {
    id: UID,
    name: String,
    power_level: u64,
    rarity: u8,
  }

  public fun new(
    name: String,
    power_level: u64,
    rarity: u8,
    ctx: &mut TxContext,
  ): Weapon {
    Weapon {
      id: object::new(ctx),
      name,
      power_level,
      rarity,
    }
  }

  public entry fun mint_weapon(
    name: String,
    power_level: u64,
    rarity: u8,
    recipient: address,
    ctx: &mut TxContext,
  ) {
    let weapon = new(name, power_level, rarity, ctx);
    transfer::public_transfer(weapon, recipient);
  }

  public entry fun upgrade_weapon(
    weapon: &mut Weapon,
    new_power_level: u64,
    new_rarity: u8,
  ) {
    weapon.power_level = new_power_level;
    weapon.rarity = new_rarity;
  }

  public entry fun transfer_weapon(
    weapon: Weapon,
    recipient: address,
  ) {
    transfer::public_transfer(weapon, recipient);
  }

  public entry fun burn_weapon(weapon: Weapon) {
    let Weapon {
      id,
      name: _,
      power_level: _,
      rarity: _,
    } = weapon;
    object::delete(id);
  }
}

This sample models a straightforward owned object lifecycle: mint, mutate, transfer, and delete. It is intentionally simple, but it matches Sui's object-based design much better than a pseudo-database or legacy RPC-style example.

1. Mint a weapon

POST /api/game/v1/assets · Create an owned object

When a player completes a quest or onboarding flow, your backend can build a transaction that calls mint_weapon. Depending on your product model, that transaction may be signed by the player, by a game-controlled signer, or through a sponsored flow. 

curl -X POST "{base_url}/api/game/v1/assets" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer {player_session_token}" \
  -d '{
    "type": "weapon",
    "name": "Blade of Dawn",
    "power_level": 12,
    "rarity": 3,
    "recipient": "{player_sui_address}"
  }'
import { Transaction } from '@mysten/sui/transactions';

const tx = new Transaction();

tx.moveCall({
  target: '{package_id}::weapon::mint_weapon',
  arguments: [
    tx.pure.string('Blade of Dawn'),
    tx.pure.u64(12),
    tx.pure.u8(3),
    tx.pure.address(playerAddress),
  ],
});

2. Upgrade a weapon

PATCH /api/game/v1/assets/{object_id} · Mutate an owned object

Upgrading changes the existing object in place. Because the Move function takes &mut Weapon, the transaction must include the current object as a mutable input. 

curl -X PATCH "{base_url}/api/game/v1/assets/{object_id}" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer {player_session_token}" \
  -d '{
    "power_level": 42,
    "rarity": 5
  }'
import { Transaction } from '@mysten/sui/transactions';

const tx = new Transaction();

tx.moveCall({
  target: '{package_id}::weapon::upgrade_weapon',
  arguments: [
    tx.object('{asset_object_id}'),
    tx.pure.u64(42),
    tx.pure.u8(5),
  ],
});

3. Transfer a weapon

POST /api/game/v1/trades · Change ownership on-chain

The simplest trade flow is a direct transfer from one player to another. In a production marketplace, you would usually combine transfer with payment, escrow, validation, or kiosk-based rules. 

curl -X POST "{base_url}/api/game/v1/trades" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer {seller_session_token}" \
  -d '{
    "object_id": "{weapon_object_id}",
    "buyer_address": "{buyer_sui_address}",
    "price_token": "SUI",
    "price_amount": "10"
  }'
import { Transaction } from '@mysten/sui/transactions';

const tx = new Transaction();

tx.moveCall({
  target: '{package_id}::weapon::transfer_weapon',
  arguments: [
    tx.object('{weapon_object_id}'),
    tx.pure.address(buyerAddress),
  ],
});

4. Retire a weapon

DELETE /api/game/v1/assets/{object_id} · Remove the object

To remove an asset permanently, consume the object and delete its UID. After that, the object is no longer available for future transfer or mutation. 

curl -X DELETE "{base_url}/api/game/v1/assets/{object_id}" \
  -H "Authorization: Bearer {player_session_token}"
public entry fun burn_weapon(weapon: Weapon) {

    id,
    name: _,
    power_level: _,
    rarity: _,
  } = weapon;
  object::delete(id);
}

Error handling and finality

Gas, stale references, execution status, reconciliation

Blockchain flows add failure modes that classic REST-only systems do not: insufficient gas, signature rejection, stale object references, and on-chain execution errors.

  • Model transaction creation, signature approval, submission, execution, and indexed state as separate states.
  • Rebuild transactions when object references become stale.
  • Store transaction digests and reconcile backend metadata from transaction effects.
  • Do not treat API acceptance as final success until on-chain execution is confirmed.
