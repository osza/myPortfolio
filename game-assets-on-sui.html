Build an octopus society on Sui

A technical/storytelling tutorial showing how a game backend and client work with Move modules, wallet signing, Sui objects, shared objects, Kiosk-style trade, and Programmable Transaction Blocks in a game where every player is one octopus living in a shared society.

Start with a society, not a loot table

Narrative context · Web2 vs Web3

Imagine you are building a game where each player is one octopus living among other octopi, trading shells and pebbles, tending communal mussel farms, and building a reputation in a shared tide pool.

In a traditional Web2 stack, that world usually collapses into rows in a studio-controlled database. The octopus identity, the shells it owns, and the farm it helps maintain are all ultimately just records the developer can rewrite at will.

On Sui, those parts of the world can be modeled as on-chain objects defined in Move. The player can hold an octopus object in a wallet, own unique shells and pebbles directly, and interact with shared structures through explicit transaction logic.

This tutorial keeps the examples intentionally simplified. The focus is on object shape, transaction flow, and system boundaries rather than full production concerns such as sponsored transactions, indexing pipelines, retries, observability, or custody design.

Architecture at a glance

Game client · Backend service · Wallet · Sui network

A common Sui integration pattern is still the same: the backend validates intent and prepares transaction data, while signing happens in a wallet or another explicitly trusted signer.

  • The game client calls your API, for example POST /api/octopus/v1/shells or POST /api/octopus/v1/farms/{farm_id}/harvest.
  • Your backend validates the request, resolves current on-chain object inputs, and builds a transaction payload.
  • The payload is returned to the client for wallet approval, or routed to an authorized signer when the product flow requires service-controlled minting.
  • The signed transaction is submitted to the Sui network.
  • Your backend stores transaction digests, reads effects, and reconciles local metadata with the resulting on-chain object state.

This keeps the API familiar for application developers without hiding the fact that the source of truth for ownership, transfer, and mutation is the Sui object model.

Before you start

Requirements: wallet, endpoint, package, indexing

  • A Sui wallet on testnet with SUI for gas, unless your flow uses sponsored transactions.
  • A current Sui full node or provider endpoint.
  • A published Move package for your octopus, shell, pebble, and farm types.
  • A backend service that can build transaction payloads and track transaction results.

Replace {package_id}, {octopus_object_id}, {shell_object_id}, {farm_object_id}, and wallet addresses with real values from your environment. Keep private keys, admin capabilities, and RPC secrets out of client code and out of source control.

Move: Define the core game objects

Smart contract logic · Identity object · Unique belongings

In this game, the first important object is not a weapon. It is the octopus itself. That object represents the player's identity in the society, while shells and pebbles are unique belongings the octopus can own, trade, and carry between interactions.

On Sui, owned objects need a UID field and the key ability. If you want an object to be transferable with transfer::public_transfer, it also needs the store ability. 

module octopus_society::assets {
  use std::string::String;
  use sui::object::{Self, UID};
  use sui::transfer;
  use sui::tx_context::TxContext;

  public struct Octopus has key, store {
    id: UID,
    name: String,
    age: u64,
    territory: String,
    reputation: u64,
  }

  public struct Shell has key, store {
    id: UID,
    label: String,
    origin_reef: String,
    rarity: u8,
  }

  public struct Pebble has key, store {
    id: UID,
    shape: String,
    colour: String,
    rarity: u8,
  }

  public fun new_octopus(
    name: String,
    age: u64,
    territory: String,
    ctx: &mut TxContext,
  ): Octopus {
    Octopus {
      id: object::new(ctx),
      name,
      age,
      territory,
      reputation: 0,
    }
  }

  public fun new_shell(
    label: String,
    origin_reef: String,
    rarity: u8,
    ctx: &mut TxContext,
  ): Shell {
    Shell {
      id: object::new(ctx),
      label,
      origin_reef,
      rarity,
    }
  }

  public entry fun mint_octopus(
    name: String,
    age: u64,
    territory: String,
    recipient: address,
    ctx: &mut TxContext,
  ) {
    let octopus = new_octopus(name, age, territory, ctx);
    transfer::public_transfer(octopus, recipient);
  }

  public entry fun mint_shell(
    label: String,
    origin_reef: String,
    rarity: u8,
    recipient: address,
    ctx: &mut TxContext,
  ) {
    let shell = new_shell(label, origin_reef, rarity, ctx);
    transfer::public_transfer(shell, recipient);
  }

  public entry fun polish_shell(
    shell: &mut Shell,
    new_rarity: u8,
  ) {
    shell.rarity = new_rarity;
  }

  public entry fun transfer_shell(
    shell: Shell,
    recipient: address,
  ) {
    transfer::public_transfer(shell, recipient);
  }

  public entry fun retire_shell(shell: Shell) {
    let Shell {
      id,
      label: _,
      origin_reef: _,
      rarity: _,
    } = shell;
    object::delete(id);
  }
}

This gives you a cleaner fit for the society described elsewhere in the portfolio: one player, one octopus identity object, plus unique belongings that can circulate between players without pretending they are fungible tokens.

1. Mint an octopus identity

POST /api/octopus/v1/identities · Create the player character

In this world, onboarding is not "create a generic account and attach cosmetics later." It is "mint the player's octopus identity." That object becomes the anchor for age, territory, and future social actions. 

curl -X POST "{base_url}/api/octopus/v1/identities" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer {player_session_token}" \
  -d '{
    "name": "Nerida",
    "age": 4,
    "territory": "Glass Kelp Ridge",
    "recipient": "{player_sui_address}"
  }'
import { Transaction } from '@mysten/sui/transactions';

const tx = new Transaction();

tx.moveCall({
  target: '{package_id}::assets::mint_octopus',
  arguments: [
    tx.pure.string('Nerida'),
    tx.pure.u64(4),
    tx.pure.string('Glass Kelp Ridge'),
    tx.pure.address(playerAddress),
  ],
});

3. Polish a shell in place

PATCH /api/octopus/v1/shells/{object_id} · Mutate an owned object

Some changes should mutate the existing object instead of replacing it. Here, polishing a shell improves its rarity in place. Because the Move function takes &mut Shell, the transaction must include the current shell as a mutable input. 

curl -X PATCH "{base_url}/api/octopus/v1/shells/{object_id}" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer {player_session_token}" \
  -d '{
    "rarity": 5
  }'
import { Transaction } from '@mysten/sui/transactions';

const tx = new Transaction();

tx.moveCall({
  target: '{package_id}::assets::polish_shell',
  arguments: [
    tx.object('{shell_object_id}'),
    tx.pure.u8(5),
  ],
});

4. Trade in the tide pool

POST /api/octopus/v1/trades · Direct transfer or Kiosk-backed listing

Trading in this game should feel like a social exchange between octopi, not just a generic buy button. One octopus might transfer a shell directly to a neighbour, or list it in a Kiosk-style market flow for discovery, settlement, and transfer. 

curl -X POST "{base_url}/api/octopus/v1/trades" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer {seller_session_token}" \
  -d '{
    "object_id": "{shell_object_id}",
    "buyer_address": "{buyer_sui_address}",
    "price_token": "SUI",
    "price_amount": "10",
    "trade_note": "Three bright pebbles and one rare shell would also work in a custom flow."

5. Model a communal mussel farm

Shared object · Multi-player structure

A mussel farm is not a private item like a shell. It is a communal structure that several octopi can interact with. That makes it a better fit for a shared object than for a plain owned object. 

module octopus_society::farm {
  use sui::object::{Self, UID};
  use sui::tx_context::TxContext;

  public struct MusselFarm has key {
    id: UID,
    total_mussels_ready: u64,
    last_harvest_epoch: u64,
  }

  public fun new_farm(
    total_mussels_ready: u64,
    last_harvest_epoch: u64,
    ctx: &mut TxContext,
  ): MusselFarm {
    MusselFarm {
      id: object::new(ctx),
      total_mussels_ready,
      last_harvest_epoch,
    }
  }

  public entry fun restock_farm(
    farm: &mut MusselFarm,
    added_mussels: u64,
  ) {
    farm.total_mussels_ready = farm.total_mussels_ready + added_mussels;
  }

  public entry fun harvest_farm(
    farm: &mut MusselFarm,
    harvested: u64,
    current_epoch: u64,
  ) {
    farm.total_mussels_ready = farm.total_mussels_ready - harvested;
    farm.last_harvest_epoch = current_epoch;
  }
}

The important design point is not the arithmetic. It is that the same farm object can be referenced and mutated through game rules by multiple players, which is exactly the communal pattern the octopus society requires.

6. Harvest with a Programmable Transaction Block

POST /api/octopus/v1/farms/{farm_id}/harvest · Bundle player and shared-state actions

A trip to the farm is rarely a single isolated state change. In one visit, an octopus might check the shared farm, harvest what is ready, update its own contribution trail, and receive mussels into personal inventory.

That is the kind of flow where Programmable Transaction Blocks become especially useful, because the player approves a single bundled action instead of a chain of disconnected mutations. 

curl -X POST "{base_url}/api/octopus/v1/farms/{farm_object_id}/harvest" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer {player_session_token}" \
  -d '{
    "octopus_id": "{octopus_object_id}",
    "harvest_amount": 8,
    "deposit_to_inventory": true
  }'
import { Transaction } from '@mysten/sui/transactions';

const tx = new Transaction();

tx.moveCall({
  target: '{package_id}::farm::harvest_farm',
  arguments: [
    tx.object('{farm_object_id}'),
    tx.pure.u64(8),
    tx.pure.u64(currentEpoch),
  ],
});

7. Fair randomness for discovered items

Rarity outcomes · Trust in shared systems

Randomness matters in this game too. A newly discovered pebble may vary in shape, colour, or rarity, and a seasonal farm event may produce an unexpectedly strong yield.

The design goal is not only surprise. It is trust. If the game says that a rare shell or pebble came from chance, players should be able to treat that outcome as a chain-backed result rather than a server-side claim they simply have to accept.

Retire a shell when it leaves the world

DELETE /api/octopus/v1/shells/{object_id} · Remove the object

Some objects should disappear permanently. If a shell is intentionally retired from the world state, consume the object and delete its UID. After that, it is no longer available for transfer or mutation. 

curl -X DELETE "{base_url}/api/octopus/v1/shells/{object_id}" \
  -H "Authorization: Bearer {player_session_token}"
public entry fun retire_shell(shell: Shell) {
  let Shell {
    id,
    label: _,
    origin_reef: _,
    rarity: _,
  } = shell;
  object::delete(id);
}

Error handling and finality

Gas, stale references, execution status, reconciliation

Blockchain flows still add failure modes that a REST-only system does not: insufficient gas, signature rejection, stale object references, and on-chain execution errors.

  • Model transaction creation, signature approval, submission, execution, and indexed state as separate states.
  • Rebuild transactions when object references become stale.
  • Store transaction digests and reconcile backend metadata from transaction effects.
  • Do not treat API acceptance as final success until on-chain execution is confirmed.
  • Be especially careful with shared objects such as communal farms, where concurrency and current object state matter directly to transaction validity.
